id = "010"
title = "Tab drag into another window's tab strip must work across processes"
tier = "hard"
+++

Problem: since 005 (tear_off.rs) every torn-off tab lives in its own Sintec.PDF PROCESS. Dragging a tab onto another window's tab strip no longer joins it: chrome.rs `tab_drag` only finds target windows via `app.window_geometry` (same process), so windows of other processes are invisible; doc_windows.rs `move_tab` only moves between windows of one process. Result today: drop over another window does nothing/opens a new window.
Goal: dropping a tab (drag started in window A, process P1) over the tab strip of window B (process P2, or same process) adds the document to B and removes it from A, at the gap under the pointer. Must work in both directions and with unsaved work (reuse the hand-off mechanism: saved file -> path, unsaved -> recovery entry; the source closes the tab only after the target confirmed it took it; on failure the tab stays and a notice shows).
Suggested design: each process publishes its window strips' screen rects (small file in a per-user temp/app-data dir, or a local named pipe / localhost socket with pid + rect + endpoint, removed on exit/stale pid check). On drop, if the pointer is over a foreign strip, send a 'take this document' message (HandOff + insert position) to that process; show the 'Release to move it to that window' label for foreign strips too. Windows only needs to be solid (project is Windows-first); keep other platforms compiling.
Constraints: no panics/unwraps on IPC input (validate everything; this is untrusted local input, reuse valid_recovery_key etc.), no hangs when the other process is dead (timeouts), no unbounded growth. Do not change the single-process fallback behaviour.
Done when: regression tests for the message parse/validation, the geometry registry (stale entries ignored), and the drop decision; a manual-check note in reports/<id>.md of what to try with two windows. fmt, clippy, cargo test for ui-egui green.
