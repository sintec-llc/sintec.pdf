User feedback on build 0.2.7 (after 011): widening/narrowing a text box with its side width handles still has problems. Exact symptom not given; find it by reproducing in the real code paths, not only with the 400-px test harness.

Known gaps from the 011 report (crates/ui-egui/src/edit_text_ui.rs, object_ui.rs, canvas.rs):
- The right-hand width handle of an open box is covered by the floating "Format text" panel (text_panel.rs / panels.rs); the panel takes the press before the handle. Check hit order / layer order, and that a handle under the panel is still grabbable (or the panel never covers it: placement).
- Width handles exist only on upright and upside-down pages; on 90/270 pages only the grip is drawn. Make them work there too.
- Width drag: min width clamp, committed width = rect width + preview delta; check it against zoom != 100%, page scroll while dragging, boxes near the page edge/right page border, and that the text reflows to the new width and the result persists (EditTextBlock width) after commit, undo/redo, save and reopen.
- Press-order: object_ui marquee vs on_move_grip (any new grab zone outside the box must be added to on_move_grip).
- A box with auto width (single line, not yet a paragraph box): does a handle drag turn it into a fixed-width paragraph box?
Write tests that reproduce each confirmed failure first (at a window size where the panel is present, several zoom levels, rotated pages), then fix. Features otherwise unchanged. Report root causes confirmed.
Done when: new tests pass; cargo fmt --all --check, cargo clippy --workspace --all-targets -- -D warnings, cargo test -p pdfcraft-ui-egui green.
