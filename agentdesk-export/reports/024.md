# 024: PDF compression: effective algorithms + Strong/Medium/Light menu with estimated output sizes

Branch `auto/024` at bf28308f; tiers hard.

## Brief

Runs AFTER the PdfCraft v0.9.0 sync (tasks 021-023, 018, 019), on the new base. Goal: make PDF size reduction really effective and let the user choose.
1. Study what exists: crates/optimize (+ crates/engine/src/optimizer.rs, "optimize.reduce" -> reduce_file_size in ui-egui, Dialog::Optimize "optimize.advanced", automation tools). Measure on synthetic and real-like PDFs (scanned pages, photo-heavy, text-heavy, many duplicate fonts/images, uncompressed streams): what is already done (flate recompress, object streams, dedupe, unused-object removal, image downsample/JPEG recompress, font subsetting, metadata strip) and where the bytes go.
2. Implement the missing effective techniques, each with tests: recompress images (downsample to a target DPI by quality level; re-encode JPEG at a quality level; convert lossless flate photos to JPEG; 1-bit scans keep CCITT/JBIG2-like or flate with predictor), better flate (max level / zopfli-style only if a pure-Rust dep is acceptable under deny.toml and AGENTS.md - otherwise use the best level of the existing crate), object streams + xref streams, dedupe identical streams and images, subset/drop unused fonts, remove unused resources, thumbnails, metadata, embedded files only when the level allows. Never change page appearance beyond the level's documented image downsampling; never lose text, forms, signatures-need-warning, bookmarks or links at Light/Medium.
3. Three presets: Light (lossless only: structure/stream recompression, dedupe, cleanup), Medium (images to ~150 dpi, JPEG ~75), Strong (images to ~100 dpi, JPEG ~55, strip extras). Put the preset table in one place and in docs.
4. UI: the "Reduce file size" command opens a small dialog (English + Russian strings; add to ru.tsv with a leading TAB and empty context, check line endings, byte-level edits, then `python zz_rehash.py crates/ui-egui/src/i18n/ru.tsv`) with a radio choice Strong / Medium / Light. Next to each choice show the ESTIMATED resulting file size (and % saved) BEFORE the user picks. Estimation must be cheap and honest: compute it from the document (sum of image bytes at the new dpi/quality estimated by a sampled trial-encode of a few images or a size model, plus the non-image bytes after lossless recompression) on a worker thread without freezing the UI, show 'calculating...' meanwhile, and label values as approximate (~). Cancel leaves the file untouched; the real result after applying is shown in a toast (before/after).
5. Keep the Advanced optimize dialog working; automation/CLI tool gets a `level` parameter (light|medium|strong) with the same presets.
Constraints: Sintec branding, en+ru only, never-panic rules for new non-test code (AGENTS.md §4), no unwrap on input-derived values, large files must not block the UI. Done when fmt, clippy --workspace --all-targets -D warnings, cargo test --workspace are green, with tests for each preset's size ordering (strong < medium < light < original on a fixture with images) and for the estimator being within a stated tolerance of the real result. Report: techniques added, measured savings per fixture and level, estimator accuracy, limitations.

## Worker summary

Reduce File Size now opens a small dialog with Strong, Medium and Light. Each level shows an estimated size (`~27.1 KB (97% smaller)`) worked out on a worker thread, with "calculating…" until it arrives. Cancel writes nothing, and after Reduce a notice gives the real before and after sizes. On every test document, Strong < Medium < Light < original, and the estimates came within 0.5% of the real result.

Formatting and clippy (`-D warnings`) are clean on the six crates I touched. All tests in filters, cos, optimize, engine, automation and the UI library pass, as do the UI create, viewer and Russian-catalogue guard tests, `xtask layers` and `xtask assets`. I did not run the full `--workspace` sweep or the wasm check; following CLAUDE.md, I left those to CI.

**Techniques added:**
- **Lossless recompression of every stream:** each stream stored with Flate, LZW, RunLength, ASCII85, ASCIIHex or no filter is re-encoded with Flate at the best level. Image data, 1-bit scans included, also gets PNG predictors. A stream is replaced only if the result, dictionary included, is smaller.
- **Tighter structure:** optimized copies pack 400 objects per object stream at the best Flate level (new `best_compression` save option).
- **Images:**
  - An image that wasn't JPEG stays lossless when that is smaller than the JPEG would be (charts, screenshots).
  - A JPEG that isn't resampled is re-encoded only if that saves at least 10%.
  - Images are never resampled upwards.
- **Presets:** defined once in `crates/engine/src/optimizer.rs`, documented in `docs/file-size-levels.md`.

| Level | Images | Discarded besides thumbnails and alternate images |
|---|---|---|
| Light | unchanged (lossless only) | nothing |
| Medium (default) | above 200 ppi resampled to 150; JPEG 75 | nothing |
| Strong | above 130 ppi resampled to 100; JPEG 55 | print settings, document info and XMP metadata, other applications' private data, broken links, unused named destinations |

Light and Medium keep text, forms, comments, attachments, bookmarks, links and tags. Signed documents are refused and the dialog says why.
- **Automation:** `doc_reduce` takes `level` (light, medium or strong; Medium if omitted). The new read-only `doc_reduce_estimate` returns the same estimates as the dialog.

**Bug fixed along the way:** Strong, and the Advanced optimizer with any "discard user data" box ticked, failed on files that had none of that data. Every Strong run on the fixtures hit it before the fix.

**Measured savings** (synthetic fixtures in `crates/engine/tests/reduce_levels.rs`):

| Fixture | Original | Light | Medium | Strong |
|---|---|---|---|---|
| Photos (3 at 300 ppi) | 4.46 MB | −27% | −98.8% | −99.4% |
| Scans (2 grey, one 1-bit) | 2.78 MB | −9.5% | −95.7% | −98.5% |
| Text (12 copies of one font, thumbnails) | 1.05 MB | −93.8% | same | same |
| Mixed report | 2.01 MB | −88.8% | −96.1% | −96.6% |

The synthetic photos are smoother than real ones, so real files will shrink less at Medium and Strong. The old Acrobat-style defaults, run on the new pipeline, give smaller scans than Medium (91 KB against 119 KB) because they use JPEG 60 rather than 75.

**Estimator accuracy:** every estimate was within 0.5% of the real size, even with a zero budget where most work is predicted. The tests allow 5%, and 25% for sample-only estimates. Estimates are less exact when images of the same kind differ a lot.

**Limitations:**
- No font subsetting; fonts and other resources a page lists but never uses stay (only unused images and forms are dropped).
- No JBIG2 or CCITT encoder: 1-bit scans get Flate with a predictor instead.
- No zopfli (no pure-Rust dependency in the tree); Flate level 9 is used.
- On the web the estimate runs on the UI thread, since there are no worker threads there.

NOTES:
- Reduce levels live only in `pdfcraft_engine::optimizer::Level` (`settings()`, `discard()`); `docs/file-size-levels.md` repeats the table and must change with it. `Session::reduced_bytes` now takes a `Level`; `estimate_job`/`EstimateJob::run` give the estimates.
- `optimize::Settings` has a new `recompress_streams` field (default on) and `Stage::Streams`; `SaveOptions` has a new `best_compression` field. The progress-bar fractions changed (images take 0.05–0.70).
- `remove_hidden` returns `NothingToApply` when nothing matched; the engine's `discard_hidden` treats that as "nothing discarded". Reuse it anywhere a discard is optional.
