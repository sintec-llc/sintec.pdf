# 015: Text box frame must match the real wrap boundary

Branch `auto/015` at 41477a6a; tiers hard.

## Brief

Task 015: make Edit PDF text box frames show the width the text really wraps at, and make a width drag set a width the engine really uses.

Problem: after a width-handle drag, the UI keeps a UI-only width (DocView.kept_width, KeptWidth) and widens block.rect in keep_width (crates/ui-egui/src/edit_text_ui.rs:372-407). The engine ignores it: block.rect is only the ink extent (crates/edit/src/text.rs TextBlock ~line 360), and rewrite_block_with_limit (text.rs ~1976-1983) picks width from style.width, else the block extent clamped to one em, or to the page margin for a single line. Hard row breaks are kept (crates/edit/src/text_regions.rs ~244-247, rewrite_styled_block ~235; width logic ~378 and ~641-642).

Goal:
1. Expose the effective wrap width from the engine, as a TextBlock field or a helper next to text_blocks, using the same rules as rewrite_block_with_limit. Cover single-line, multi-line paragraph, table cell, single-word cell and rotated pages.
2. Draw the frame's left/right edges (top/bottom when the page is quarter-turned, see width_is_vertical) from that width, in canvas.rs and DocView::shown_text_boxes (canvas.rs ~583).
3. A width drag must set a width the engine uses on the next rewrap, e.g. via BlockStyle.width. If a UI-only width can't be made real, clamp or drop it so the frame never lies.
4. Keep 014 behaviour: no snap-back after drag, narrowing rewraps, clamp to longest word, no merging of table rows or cells.
