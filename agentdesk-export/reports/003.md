## Brief

Task 003: bigger, reliable move handle for paragraph text boxes in Edit PDF (Sintec.PDF, a PdfCraft fork).

Current state (crates/ui-egui/src/edit_text_ui.rs):
- `BlockDrag` struct ~L362 (fields page, block, generation, start, grip); `Grip` enum just above it (Move, Left, Right).
- `EDGE_REACH` = 6.0 ~L373. `width_handles` ~L376 draws only two 7×h edge handles (left/right). There is NO move handle yet, so add one.
- `edge_at` ~L383 and `grab_at` ~L398 (topmost box wins; edges only when `upright`; otherwise Move if `b.contains(p)`).
- In `page_input` ~L711-732: drag start uses `ui.input(|i| i.pointer.press_origin())` with `grab_at`. Hover path calls `draw_handles(boxes[hit])` (L730) and sets cursor at L732 (ResizeHorizontal on edge, else Text). Cursor must become a move cursor (CursorIcon::Move or similar) over the move handle.

3. Reliable start: decide the grip from press_origin (already done), and make sure a fast move or the pointer leaving the box does not drop the drag. Check whether `active`/`view.block_drag` continue to update when the pointer leaves the box rect.
4. Hover cursor: move cursor over the handle.
5. Any new UI string needs a ru.tsv line (TAB-prefixed, check for `\r` first; project notes say this tree is LF). Then run `python zz_rehash.py crates/ui-egui/src/i18n/ru.tsv`. Only if you add a string. Also check whether a tooltip is needed.

Look at how existing tests open a PDF, select a text block, and drag. Write a test that drags a paragraph by its move handle and asserts the block's position changed (for example via the pending edit or the block's bounds). Use synthetic fixtures only.

Constraints (CLAUDE.md/AGENTS.md): never panic in non-test code. No unwrap/expect, no indexing with input-derived positions, and use `get` on `boxes`. No unsafe. Work in the worktree only.

Gates before done: `cargo fmt --all --check`, `cargo clippy --workspace -- -D warnings`, `cargo test -p pdfcraft-ui-egui` (or the workspace). Commit with a message beginning `Task 003:` and the attribution line. Do not push. Do not use bare git stash.

## Worker summary

Paragraph boxes in Edit PDF now have a move grip, and dragging a paragraph by it moves the paragraph. `cargo fmt --all --check`, `cargo clippy --workspace -- -D warnings` and `cargo test -p pdfcraft-ui-egui` pass, and everything is committed (`Task 003:`) and not pushed.

**Grip geometry**
- **Drawn grip:** an 18×18 px rounded accent-coloured square with a white four-way arrow, sitting directly above the box's top-left corner, so it stays off the text.
- **Hit area:** 24×24 px (the drawn square plus 3 px on every side). It wins over box bodies and edges.
- **Page top:** if a box sits against the top of the page, the grip is drawn just inside the box's top-left corner instead of above it. That overlaps the text slightly, but only in that edge case.
- **Cursor:** the move cursor shows over the hit area.

**Other changes** (`edit_text_ui.rs` and `object_ui.rs`)
- **Marquee conflict:** a press on the grip used to start a marquee selection, because `object_ui::page_input` claims any press on empty page first. That is why the first version of the test never started a drag. `object_ui.rs` now declines presses that land on a grip, using a new `edit_text_ui::on_move_grip`.
- **Drag continuity:** the drag now falls back to `latest_pos()` when `interact_pos()` is missing, so a fast flick or leaving the box keeps the drag going. Releasing still ends it via `drag_stopped` or no button down.
- **Body and edges:** dragging the body and the edge resize work as before.
- **Click on the grip:** a plain click on the grip does not open the text editor.
- **Strings:** I added no UI strings and no tooltip, so there is no `ru.tsv` change.

**Test:** `dragging_a_paragraph_by_its_move_handle_moves_it` in `tests/editing.rs` hovers the grip and checks for the move cursor. It then presses 4 px off the grip's centre, drags 30 pt right and 40 pt down, and checks the block moved and the history shows "Move object". The other 12 paragraph-drag tests in `editing.rs` still pass.

NOTES:
- In Edit text & images, `object_ui::page_input` runs before `edit_text_ui::page_input` and turns any press on empty page into a marquee, so new handles outside a box's rect must be exempted there (see `on_move_grip`).
- Grip constants and hit logic: `MOVE_GRIP`, `MOVE_GRIP_SLOP`, `move_handle`, `handle_at` in `edit_text_ui.rs`.
