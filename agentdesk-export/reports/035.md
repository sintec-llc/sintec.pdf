# 035: Flaky ui-egui tests on Windows: d3d10warp.dll access violation when wgpu tests run in parallel

Branch `auto/035` at edabce60; tiers standard.

## Brief

Finding: `cargo test -p pdfcraft-ui-egui --test content` (and probably other egui_kittest+wgpu test binaries) crashes about 1 run in 6 on Windows with STATUS_ACCESS_VIOLATION (0xc0000005); Windows Application log (event 1000) names the faulting module d3d10warp.dll (Windows WARP software rasterizer, driven by wgpu). Each crashing test passes alone (15/15) and with --test-threads=1 (14/14): it is a race when several tests create/use a wgpu D3D device in parallel threads. Not our code (unsafe_code is forbidden), but it makes cargo test and CI red at random and stops `cargo test --workspace` at the first crashed binary.
Goal: make this deterministic without hiding real failures. Options, pick the least invasive and verify: (a) a shared test helper that serialises creation/use of the kittest wgpu harness behind one global Mutex (poison-tolerant) used by all ui-egui test binaries; (b) a harness config that renders without wgpu where the test needs no pixels (egui_kittest without wgpu for logic tests, wgpu only for snapshot tests); (c) per-crate test-threads limit through .cargo/config.toml - last resort, as it slows all tests and does not cover CI. Check .github workflows too (the CI runner for Windows must benefit as well).
Done when: `cargo test -p pdfcraft-ui-egui` passes 10 times in a row on this Windows machine with default threads (script it, report counts), fmt and clippy -D warnings are green, and the report states which option was used and the before/after crash rate.
