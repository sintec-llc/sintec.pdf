# 033: Text edit field: preview of a substituted font differs from the final result and the original

Branch `auto/033` at ce2c370d; tiers hard.

## Brief

Still wrong after task 027 (build 0.3.0): when the original font is replaced by a substitute (not embedded / not installed), the text shown in the in-place edit field (preview while typing) looks different from (a) the final rendering after the edit is committed and (b) the original font. Expected: the preview uses exactly the same font face, weight, style, size, letter/word widths and line wrapping as the committed result, and the substitute is the closest metric-compatible match to the original (glyph widths, see tasks 004/006/027).
Where: crates/ui-egui (edit_text_ui, canvas, text_panel, fonts/text_fonts), the engine side that renders the committed text. Find the divergence: probably the egui editor uses a different font family/fallback chain than the engine's final render. Make both go through one font-resolution function. Add tests that the resolved face for a given (original font name, flags) is identical for preview and commit, and a metric test on widths. Use the PDFs available in the repo test fixtures; if a table-like PDF with Cyrillic text is available, use it. Never use fonts from Adobe or installed system fonts for embedding (AGENTS.md). Done when fmt, clippy -D warnings and cargo test (touched crates) are green; describe a manual check.

## Worker summary

I fixed the preview/commit mismatch: the edit field and the committed edit now pick the substitute font through one function and apply one fitting rule. fmt, clippy `-D warnings`, and the edit, engine and ui-egui tests all pass, and `xtask layers` is OK. `xtask assets` fails on three files in `.tmp026/` (scratch JPGs left by task 026, not tracked by git); this change adds no assets.

**Where they diverged**
1. **Fonts the PDF doesn't embed** (or embeds in a form the editor can't load) were previewed in the app's own interface font. That matched neither the original nor the result.
2. **At commit, the substitute was picked by guesswork.** The edit used whichever font already loaded into the page looked closest. That could be a different face from the one previewed, for example a bold face loaded by an earlier edit.
3. **Preview size and spacing didn't match.** The commit resizes the substitute to the original's capital height and widths; the preview drew it at its natural size and spacing, so line wrapping differed.
4. **The substitute was chosen once, from the text at that moment.** The commit chooses from the final text, so typing new kinds of letters could change the commit's choice but not the preview's.

**What changed**
- **One way to pick the face (`stand_in`).** The preview, the Format text panel and the commit all use it. The commit now records which loaded font replaces which original font (new `BlockStyle::substitutes`), and the edit uses that mapping before falling back to the old guess. After the Font substitution dialog it goes through the same function.
- **One sizing rule (`substitute_fit`).** It works out size, width and weight adjustment from the original font's details and the substitute's font file. Both the commit and the preview use it.
- **The editor (`edit_text_ui`).** Every font in the paragraph now gets its substitute in the preview, including non-embedded ones. Letters the commit will draw in the substitute are drawn in it at the fitted size and advance exactly as far as the commit sets them. The engine decides which letters those are (`Document::substitute_chars`), by the same steps the commit takes. When newly typed letters would make the commit choose a different face, the preview switches too.
- **`parity/`** notes and test references for `edit.font-reuse-substitution` are updated.

**Tests** (I confirmed each new one fails when its fix is reverted)
- `a_font_without_a_program_is_previewed_and_drawn_in_one_stand_in`: a non-embedded Calibri-Bold with Carlito-Regular as the substitute and a decoy bold face already loaded. The preview and the commit use the same face file and the same fit, and the commit doesn't take the decoy.
- `stand_in_letters_advance_as_far_as_the_edit_sets_them`: the width test. Previewed substitute letters advance by their width × size × fitted size × fitted width scale, the same formula the commit uses.
- Two edit-crate tests: `substitute_fit` behaviour and `substitute_chars`.

The repo has no Cyrillic table PDF, so the tests use small generated PDFs and a generated font.

**Still not identical** (written in the parity notes)
- The preview spaces letters exactly as committed but can't stretch the glyph shapes horizontally or draw the faux-bold outline, so substitute letters look slightly narrower or lighter.
- For a non-embedded font, the preview shows the whole run in the substitute. The page renderer still draws the original text with its built-in standard font, which the editor can't load.

**Manual check:** open a Cyrillic table PDF whose font isn't embedded or installed (e.g. Calibri, with Carlito as the stand-in) and choose Edit PDF. Open a cell and type Cyrillic and Latin text until it wraps. The text in the edit field should keep the original text's apparent weight, letter height, spacing and wrap point, with no switch to the interface font. Click outside to commit: the substitute letters should keep their face, size and positions, and lines should break in the same places. The Format text panel's "Missing characters: …" line should name the same face. Repeat with a bold heading after a bold face from another family has been loaded into that page by an earlier edit: the committed letters must use the face the panel names, not that other bold face.

NOTES: `pdfcraft_engine::substitute_fit(facts, face_bytes)` is the one fitting rule for a substitute face, used by both the preview and the commit; `Document::substitute_chars` says which letters the commit draws in the substitute.
`BlockStyle::substitutes` (original font resource → loaded `PCFull…` resource) beats `registered_substitute`'s guess. Compare styles with `BlockStyle::is_plain()`, not `== default()`.
In egui 0.36, `FontTweak.scale` only scales how glyphs are drawn, not how far they advance, so spacing has to be adjusted per letter (as `editor_job` does).
