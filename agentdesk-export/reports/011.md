# 011: Text box move grip / width handles: make them reliable

Branch `auto/011` at 905250ef; tiers standard.

## Brief

Goal: make the paragraph-box move grip and both width handles reliable (task 011). Grip and side handles must be visible and grabbable for the hovered OR selected/being-edited box. Hit areas must be at least 24px. A grab must continue until release wherever the pointer goes. Side-handle drags must always change the width, including while editing. Rotated pages must work too.

Files (crates/ui-egui/src/edit_text_ui.rs unless noted):
- Constants and geometry: EDGE_REACH (~l.373), width_handles (~l.376, 7px wide, height clamped 14-28), MOVE_GRIP/MOVE_GRIP_SLOP (~l.382), move_handle (~l.388, clamped to bounds only at the page top), handle_at (~l.394), edge_at/grab_at (~l.408-428; edges only when upright).
- page_input (~l.659). Known problems:
  - ~l.766: the hover position is dropped unless xf.rect.contains(p), so the grip above a box near or past the page top is lost.
  - ~l.767 and ~l.773: grip and handles are gated on active.is_none(), so they vanish while editing. ~l.687 gates upright for handles.
  - ~l.758-765: drag start uses press_origin, but it only runs for active.is_none().
  - ~l.719-720: the live preview clamps width at 12px.
  - ~l.735: the committed width depends on the l.rect width plus the preview delta.
  - ~l.728: drag ends on drag_stopped() or when no pointer is down.
- object_ui.rs ~l.249: on_move_grip is checked only when view.line_editor.is_none(). While editing, a grip press falls through to selection/marquee. Object_ui runs before edit_text_ui (see project notes).
- canvas.rs ~l.2851-2881 decides call order and allow_interaction.

Constraints (CLAUDE.md/AGENTS.md): never panic in non-test code (no indexing with input-derived positions; use get). No unwrap/expect. No unsafe. New UI strings need ru.tsv rows; rerun python zz_rehash.py crates/ui-egui/src/i18n/ru.tsv. Working-tree files may be CRLF. Keep layering rules.

Tests: add egui_kittest tests in crates/ui-egui/tests/editing.rs (or a new file). See rotated_pages.rs for rotated-page setup, and set app.fonts.installed_override per project notes. Cover: (1) hover the box, then move the pointer up onto the grip; the grip stays grabbable. (2) Drag the grip; the box moves (MoveObjects edit). (3) Drag each side handle; the width widens or narrows (EditTextBlock with width). (4) Same while a box is being edited. (5) A rotated page; the grip must still work.

Done when: the new tests pass, cargo fmt --all --check, cargo clippy --workspace -- -D warnings and cargo test -p pdfcraft-ui-egui are green. Report the root causes you confirmed by reproducing them.

## Worker summary

The move grip and both width handles now work, and the new tests pass. `cargo fmt --all --check` and `cargo clippy --workspace -- -D warnings` are clean, and `cargo test -p pdfcraft-ui-egui` passes in full.

**What was wrong (reproduced by running the new tests against the old code)**
1. **Marquee took the edge press.** `object_ui` starts a marquee for any press that isn't on a text object. The width handles reach outside the box, and only the move grip was exempt, so a press on the outer half of a handle started a marquee. The width drag never began. Two of the new tests failed on the old code for this reason.
2. **Handles were too small.** The hit strip was about 12px wide and the drawn handle 7px by 14–28px.
3. **Editing blocked the drag.** Drag start, the grip hit-test and the handle drawing were all gated on `active.is_none()`. While a box was open for typing, `object_ui` also skipped its grip check. The grip and handles vanished and a press fell through to selection or a marquee.
4. **Hover required the page rect.** The hover position was dropped unless it was inside `xf.rect`.

**What changed**
- **`edit_text_ui.rs`:**
  - Handle hit strips are now 24px wide: 14px outside the box edge and 10px inside. For the box being edited they reach outside only, because the inside belongs to the text editor.
  - The drawn handles are bigger.
  - The grip and handles show for the hovered box and for the box open for typing.
  - Hover is tracked slightly past the page edge.
  - The drag already followed the pointer anywhere until release; I kept that and added a named minimum width.
  - A press on the open box's own grip or edge starts the drag directly. The drag keeps the editor open, and on release the typed draft goes into the same `EditTextBlock` edit.
  - `on_move_grip` now also covers the width-handle strips.
- **`object_ui.rs`:** the `line_editor.is_none()` gate on the grip check is removed.
- **Tests:** `crates/ui-egui/tests/text_box_grip.rs` has five tests.
  - Climbing from the box onto the grip, then dragging it.
  - Dragging the grip far off the box and page.
  - Each side handle widening and narrowing, pressed 8px outside the box.
  - The grip and the left handle while the box is being edited.
  - The grip on pages rotated 90, 180 and 270 degrees.

**Not done**
- Width handles still only exist on upright and upside-down pages; on 90/270 pages only the grip is drawn.
- The right-hand width handle of an open box can't be tested at this window size, because the floating "Format text" panel covers it. The editing test uses the left handle.
- The hover-from-box-to-grip and plain grip-drag tests pass on the old code too, so they are regression guards, not reproductions.

NOTES:
- A press outside a text object's rect starts an `object_ui` marquee unless `edit_text_ui::on_move_grip` returns true. Any new grab zone outside the box must be added there.
- Tests that edit text need `app.fonts.installed_override = Some(standard_faces())`. With an empty list the click opens the font-substitution flow, not the editor.
- The floating "Format text" panel sits over the right edge of an open box and takes the pointer there.
