# 010: Tab drag into another window's tab strip works across processes

## Problem
Since 005 every torn-off tab lives in a Sintec.PDF process of its own. `chrome.rs::tab_drag` only
found target windows through `app.window_geometry` (this process), so a tab dropped on the strip
of a window of another process did nothing.

## Design (`crates/ui-egui/src/tab_transfer.rs`)
- **Registry.** Each process writes `<pid>.json` in `Windows` beside the recovery folder
  (`%LOCALAPPDATA%\Sintec.PDF\Windows`, the portable data folder, or the platform's data folder).
  It holds the pid, a loopback port, a random 128-bit token, and per window the strip's and tabs'
  rectangles in **physical screen pixels** (points × pixels-per-point, so windows on different
  scales agree). A heartbeat thread rewrites it every 2 s (at once when the strips change) and
  removes it on exit. Readers ignore their own pid, entries not rewritten for 10 s, dead pids
  (Linux, via /proc), malformed or oversized files (64 KiB), and read at most 32 peers out of
  256 files. Files older than 5 min are deleted.
- **Hand-off.** On release over a foreign strip (only outside this window, which is in front while
  it drags), the source sends one JSON line to `127.0.0.1:<port>`: `v`, `token`, `file` (saved and
  unchanged, absolute path) or `recovery` (key of the recovery entry holding unsaved work, written
  as for a tear-off), `window`, `before` (gap index) and `page`. The target checks everything
  (16 KiB cap, token compared in constant time, absolute path without control characters,
  `valid_recovery_key`, bounded gap and page), queues it for the UI (at most 4 waiting), wakes the
  UI and waits up to 4 s. The UI opens it (refusing while a dialog/prompt is open, or if the file
  is gone), moves it to the gap and answers `{"ok":true}` or `{"ok":false,"reason":code}`.
- **Source.** Closes the tab only after `ok`. Otherwise the tab stays, an unused recovery copy is
  removed and a notice says why ("Couldn't move {name} to that window: {e}. It stays here.").
  Timeouts: connect 0.5 s, reply 8 s. A dead peer fails at connect.
- If the target takes it but the source has given up (timeout), the document is open in both
  windows: never lost. A request the UI didn't take within 4 s is cancelled and never taken later.
- The in-process paths (reorder, same-process windows, tear-off) are unchanged; `decide` puts
  them first. The web has no transport (cfg-gated).

## Tests
- `tab_transfer::tests`: request round trip and 17 malformed or unauthorised requests, reply
  parsing, entry validation (stale, future, bad token, NaN, inverted, oversized, too many strips),
  registry (own pid, stale, mismatched pid, junk, oversized, foreign names, cap), target and gap
  lookup, pixel conversion, the drop decision, and over loopback: publish/withdraw, hand-off
  confirmed, refusal, wrong token, dead peer (fast), cancelled after the UI didn't answer.
- `tests/tab_windows.rs`: a real kittest drag onto a published foreign strip moves the tab (unsaved
  work as a recovery entry, gap after the first tab); a refusal keeps the tab with a notice and
  removes the copy; a dead target keeps the tab; no foreign strip means nothing happens; the
  target opens a handed-over tab at the gap, on its page, still unsaved, and refuses missing files
  and while a dialog is open.

## Manual check with two windows (Windows)
Build and run `target\...\pdfcraft.exe` with a few PDFs open.
1. Drag a tab out of the strip: it opens in a new window (process B). Arrange A and B side by side
   without overlap.
2. Drag a saved, unchanged tab from A onto B's strip, between two tabs. While over B's strip the
   label "Release to move it to that window" shows. Release: the tab appears in B at that gap and
   shows; it is gone from A. B comes to the front.
3. Edit a document in A (add a comment) without saving, drag its tab to B. In B it shows the edit
   and is still unsaved (closing it asks to save, to its original path). A doesn't ask about it.
4. Drag a tab from B back onto A's strip (the other direction), at the end of the strip.
5. Drag B's only tab onto A's strip: B's window keeps showing its Home/empty state (as with any
   emptied process window) and A has the tab.
6. Open a dialog in B (Preferences), then drag a tab from A to B: the tab stays in A and a notice
   says "that window is busy".
7. Kill process B in Task Manager, then within 10 s drag a tab from A over where B's strip was:
   at most a short pause, the tab stays and the notice says "that window has closed". After 10 s
   the label no longer appears there.
8. With A on a 150 % monitor and B on a 100 % monitor, repeat 2: the gap matches the pointer.
9. Single-process behaviour is unchanged: dragging along A's own strip reorders; pulling a tab
   out onto empty desktop opens a new window.
10. Check `%LOCALAPPDATA%\Sintec.PDF\Windows`: one `<pid>.json` per running process; files go when
    the processes exit.

## Not done
- No z-order: a foreign strip hidden under a third window still takes the drop.
- Dragging over B does not highlight B's gap in B (only the label in A).
